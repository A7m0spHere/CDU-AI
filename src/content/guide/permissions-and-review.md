在上一篇[提示词撰写思路](/guide/task-description/)里，我们聊过怎么把需求写清楚。但光在提示词里嘱咐一句“不要乱删文件”，其实只是一层口头提醒，而不是铁门锁。

只要模型获得了操作本地文件和运行命令的能力，就可能出现误判、执行跑偏，甚至被外部文本带歪。这一篇专门讲清楚两道真正的安全防线：**如何管住 Agent 的操作权限与文件安全**，以及**如何利用 Git 和验收清单做好结果检查**。

## 社区里常见的三个权限坑

很多人刚开始觉得“弹窗次次点确认太麻烦”，干脆一路放行，结果往往就出在下面这三种情况里。

### 1. 一键放行高权限，导致文件夹被误删

具备文件修改和终端命令能力的 Agent，一旦被授予过高的自动执行权限，一条理解偏差的清理命令或覆盖操作，就可能把目录里的资料直接删空。

V2EX 上就有[用户自述开放高权限后遭遇文件误删](https://global.v2ex.com/t/1233011)的经历。社区里也反复出现过“想让 AI 顺手清理临时文件，结果把整个项目或源码目录一起删掉”的讨论。被命令直接删除的文件，很多时候**不会经过回收站**，事后很难找回。

### 2. 没圈住工作范围，Agent 在电脑里“到处乱串”

不少人以为只要在对话框里说了“只改这个文件夹”，Agent 就真的看不到其他地方。

实际上，不同工具在不同模式和沙盒配置下的权限边界差异很大：有些工具在默认配置下只把**写入**限制在当前工作区，但**读取**或**执行命令行脚本**时，仍可能沿着路径访问上级目录、桌面甚至系统用户目录。如果脚本路径写错，或者读取了带恶意隐藏指令的外部文件（即[提示词注入](/glossary/prompt-injection/)），Agent 就可能越界去翻看甚至改动工作区之外的文件。

安全领域把“给模型过多工具能力、过宽访问范围、且缺少人工把关”的风险归纳为 [过度授权（Excessive Agency）](/glossary/excessive-agency/)——问题往往不在于模型故意作恶，而是权限给得太宽、一旦出错收不住手。

### 3. 顺手查了隐私文件，把敏感内容送进上下文

你的电脑里很可能放着不少不适合上传给第三方服务的内容：证件照片、个人成绩单、账号密码备忘、带有接口密钥的 `.env` 配置文件，或者本地开发凭证目录。

当 Agent 为了“了解背景”或排查问题主动搜索全盘文件时，一旦把这些内容读进去，它们就会进入当前[上下文窗口](/glossary/context-window/)；在使用云端模型服务时，相关文本也会随请求发送给远端处理（相关边界见[隐私](/glossary/privacy/)）。如果在同时联网的工具里叠加提示词注入，敏感文本还可能被间接外传。

## 管理权限与文件安全的五个实用习惯

不需要成为安全专家，养成下面五个习惯，就能明显降低日常使用中的误操作和越界风险。

### 1. 一个任务一个独立目录，重要资料先备份

永远不要直接把“桌面”“文档”或整个盘符授权给 Agent。

就像在[第一次使用 Agent](/guide/first-agent/)里专门新建 `CDU-介绍网站` 一样，只建一个**只放本次任务所需材料**的干净目录；如果是重要课程资料或正在写的代码，先复制一份副本或者做好版本存档，再让 Agent 上手。

### 2. 分清“只读”和“修改/执行”，高危操作保留确认

在工具弹出的权限提示前，养成先看一眼具体动作的习惯，不要闭眼点“全部允许”：

- **只读查看、列目录**：在限定文件夹内通常风险较低；
- **修改、覆盖或批量移动文件**：先看清目标路径，或者先让它把结果输出到新建的子目录；
- **删除文件、运行终端命令、安装依赖或对外发送数据**：尽量保持逐次确认，看懂命令在干什么再放行。

### 3. 敏感信息与密钥不要放进工作区

身份证件、私人聊天记录、账号密码和 API 密钥，不要放进给 Agent 开放的文件夹里。

如果你使用的是支持精细权限规则或系统级[沙盒（Sandboxing）](/glossary/sandbox/)的工具，可以把常用的凭证目录和敏感配置文件提前加入“禁止读取”列表，从软件和系统层面堵住越界读取，而不是只靠口头叮嘱。

### 4. 警惕来历不明的网页和外部文档

不要轻易让开启了高权限或自动命令执行模式的 Agent，直接去抓取陌生网页、打开不明压缩包里的文档并顺手执行脚本。外部文档里藏的一句隐藏文本，就可能诱导模型偏离原任务、调用手头的工具去读不该读的文件。

### 5. 大改动先走“只读出方案，确认后再写入”

整理几百份文件或重构整个项目时，先要求 Agent 只读分析并列一份操作清单，等你核对完路径和规则，再让它动手写入。把不可逆的操作拆到人工确认之后，失误代价会小得多。

## 开发项目时，用 Git 留好存档与改动对比

如果你开始用 Agent 制作网页、写小工具或做课程项目（比如使用 ZCode 这类偏开发向的工具），**Git** 是保护文件、检查改动最趁手的工具。

Git 是一套本地[版本控制](/glossary/version-control/)工具。入门时可以先把它理解成**给项目文件夹拍“历史快照”的存档机**：

- **让 Agent 动手前先存档**：先把当前能正常跑的版本做一次本地[提交（Commit）](/glossary/commit/)（或另行拷贝一份备份），再在此基础上单独新建一个[分支（Branch）](/glossary/branch/)让 Agent 修改。要注意**仅仅新建或切换分支不会自动保存未提交的本地改动**；只有先提交或备份好，中途改坏结构或误删代码时才能可靠地退回动手前的状态，不用手动重来。
- **改完直接对照“改动清单”**：Agent 汇报做完后，在工具界面或 Git 里看一眼改动对比（diff），就能清楚看到它新增了哪个文件、改了哪几行代码、有没有顺手删掉不该动的配置。这比盲目相信口头总结靠谱得多。
- **不满意就局部恢复或丢弃**：哪几个文件改偏了就只还原那几个文件，或者直接放弃这个试验分支，主线版本不会受影响。

顺带提一下 **GitHub**：如果说 Git 管的是你电脑本地的[仓库](/glossary/repository/)和历史存档，GitHub 就是把这些仓库托管到云端、方便备份和多人协作的平台。做团队项目时，大家常把改动推到各自的远程分支，发起 [Pull Request](/glossary/pull-request/) 互相检查过代码，再[合并（Merge）](/glossary/merge/)进主分支——CDU AI 这个网站本身的日常维护就是这样协作的。

不过，把项目同步到 GitHub 前多留一个心眼：**如果仓库是公开的，推送前一定要检查待提交的文件列表，配合 `.gitignore` 屏蔽 `.env` 密钥文件、本地数据备份和个人隐私材料**，避免让 Agent 顺手生成的配置或敏感文件一起传到公开网络上。同时要记住，**`.gitignore` 只对未跟踪文件生效，对已经被 Git 跟踪入库的文件无效**；如果敏感文件此前已经提交过，需要额外将它移出版本跟踪并更换已暴露的密钥。

## 任务做完别急着收工：结果检查清单

权限和 Git 管的是“别出大事、出事能找回”，结果检查管的是“真的做对了没有”。

不要以为 Agent 在对话框里回复“全部完成、测试已通过”就万事大吉。社区里就有过[Agent 声称测试通过，但实际打开页面按钮根本无法使用](https://www.reddit.com/r/ClaudeCode/comments/1ul904x/my_claude_code_agents_kept_saying_done_all_tests/)的真实吐槽。拿到产出后，建议按这四步做一次[验收](/glossary/acceptance/)：

1. **先看改动范围**：结合 Git 改动记录或文件夹列表，核对它新建、修改、删除了哪些文件，确认没有误删原文件，也没有在工作区外留下多余改动。
2. **按真实场景亲自跑一遍**：网页要双击打开并逐个点击按钮、切换手机宽度看看排版；整理后的文件夹要抽查几份文件有没有分错类；表格公式和代码输出要自己实际验证，不能只看 AI 的口头总结。
3. **对照一手资料核查事实**：凡是涉及政策通知、课程要求、数据引用或代码行为的细节，以官方文件或实测结果为准，排查是否存在[AI 幻觉](/glossary/hallucination/)。
4. **确认可用再存档或覆盖**：核验无误后，再提交新的 Git 快照，或把成果替换进正式文件夹。

## 常见误区与边界提醒

- **“我电脑里都是作业，没什么可偷的”**：误删快截止的课程报告或毕业设计本身就是最痛的损失；而且平时保存的表单截图、登录凭证和配置文件，往往就在不经意间躺在同一块硬盘里。
- **“用了 Git 就万事大吉，可以随便开高权限”**：Git 只管得住已经被它跟踪管理起来的项目文件，管不住工作区外被误删的资料，也拦不住已经读进上下文并上传到云端的隐私内容。权限隔离和 Git 版本保护需要配合使用。
- **“模型越来越聪明，应该不会犯低级错误”**：模型按概率预测下一步操作，它并不真正承担后果。**最小权限、目录隔离、Git 存档、亲自验收**，这几道习惯目前都无法省掉。

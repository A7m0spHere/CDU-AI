## 1. 两层分类

术语页左侧是「分支树」，按 git graph 的方式组织：

```text
[AI] AI 主线
  ├ 基础
  ├ 提示词
  ├ 工具
  ├ Agent
  ├ 安全
  └ 成本
      ╰─→ [vibecoding] Vibe Coding
              ├ 前端 / 后端 / 产品 / 测试 / Git
```

- 分支点在主线的**末端**：主线走完 6 个 AI 分类后，用一条连接线拐到 vibecoding 分支，不并行、不抢占主线空间。
- 两个分支头（`AI` / `vibecoding`）都可以**折叠**，收起后只留分支头与计数。
- **默认停在 `AI 主线`**：打开页面先看到 AI 主分支的内容，延伸分支需要点击分支头才会展开显示，不再有「一屏看到全部」的入口。
- 分支头点击 = 按整个分支筛选（合并该分支下所有分类）；分类节点点击 = 只看该分类。
- 节点颜色跟随所在分支（主分支蓝、vibecoding 紫）；`清除筛选` 回到默认的 AI 主线。
- 延伸分支的 5 个技术类目挂在 Vibe Coding 之下：先通过 vibe coding 接触 AI 做东西，再撞到前端 / 后端 / 产品 / 测试 / Git。

## 2. 术语模块结构（页面区块）

每个术语详情页由两段组成：**必填头信息** + **可选模块区块**（frontmatter 字段驱动，不写就不渲染）。

| 页面区块 | frontmatter | 说明 |
| --- | --- | --- |
| 标题 + 英文名 | `term` / `en` | 页面 h1 |
| 你可能会说 | `youMaySay` | 读者真实会问出口的一句话，把术语和场景连起来 |
| 定义（加粗） | `definition` | 一句话释义，卡片与搜索也用这句 |
| 先知道 / 也常被叫作 | `category` / `aliases` | 分类与常见别称 |
| 校园里的样子 | `example` | 贴近校园的具体场景 |
| 场景拆解 | `scenario` | 标题 + 2–4 步**可点击**流程；每步有对应的提示画面（body，可选 quote / meta / note），支持键盘左右切换 |
| 正文 | Markdown 正文 | 核验要点、容易混淆的地方等 |
| 选择题 | `quiz` | 最多 3 题，每题 2–4 个选项，**恰好一个 correct: true**；点击即揭晓并显示解释 |
| 你可以这样告诉 AI Agent | `agentPrompt` | 可一键复制的提示词 |
| 接下来学什么 | `related` | 指向已存在词条的 id |
| 延伸阅读 · 权威出处 | `sources` | 可打开的官方文档或原始论文 |

校验：`npm run check:content` 会检查场景步骤数、题目选项数与正确答案数量、未知字段；写错直接失败。

## 3. 两类词条的写法不同

| | AI 主分支 | 延伸分支 |
| --- | --- | --- |
| 定位 | 理解与使用 | 只求「见到不懵」 |
| 正文结构 | 六段：一句话说清 / 打个比方 / 它是怎么运作的 / 你会碰到它的场景 / 常见误解 /（可选）再深入 | **四段**：是什么 / 什么时候会遇到 / 和 AI 的关系 /（可选）想深入再看 |
| 操作步骤 | 可以没有 | **一律不写**，不教前端、不教 Git 命令 |
| 篇幅 | 完整 | 300–500 字 |
| 来源 | 官方文档优先 | 官方文档或权威入门资料 |

共同硬要求：

- `sources` 至少 1 条**可打开的官方文档**；正文事实要与来源一致。
- 卡片与搜索用的一句话释义（`definition`）不超过 60 字。
- `reviewed` / `reviewedBy` 只由真人填写，页面才会从「初稿 · 尚未人工核校」切换为「已人工核校」。
- 文件名用英文短名 kebab-case（如 `context-window.md`）；`order` 同分类内从 1 递增；`related` 只能指向已存在的词条。
- 字段只能使用 schema 里定义的那些——写 `duration` 这类已废弃字段会被 `npm run check:content` 拦下。

## 4. 分批节奏

| 批次 | 内容 | 谁做 | 产出 |
| --- | --- | --- | --- |
| 批 0 | **2 条示范**：1 条 AI 主分支 + 1 条延伸分支，走完「起草 → 查证 → 人审校 → 合并」 | 人起草与签字；Agent 查证与工程 | 同时完成 #3 的真人审校演示 |
| 批 1 | `basics` 8 条 + `prompt` 8 条 | 同上 | 16 条 |
| 批 2 | `tools` 6 条 + `safety` 6 条 | 同上 | 12 条 |
| 批 3 | `cost` 5 条 + `agents` 7 条 + 延伸分支 18 条（按分支逐个小 PR） | 同上 | 30 条 |

每个 PR 只做一个分支的一批词条，便于逐条审校。

## 5. 分工

- **人**：选题、确定定义与判断、起草正文、按 [`CONTENT-REVIEW.md`](CONTENT-REVIEW.md) 第 5 节逐条核校并签字。
- **Agent**：核对来源链接是否可打开、口径是否与官方文档一致、字段与格式、内链与 `related`、搜索索引、测试与构建；不代写「亲测」，不代签 `reviewed`。

## 6. 验收（对应 #7）

- [ ] 12 个分类与页面分支树一致，空分类不渲染空分组。
- [ ] 至少一批由人审校的典型词条，准确标注审校人与日期。
- [ ] 新增 / 合并 / 删除与分类规则写入 CONTRIBUTING。
- [ ] 链接、搜索、详情路由与索引正常，`npm run verify` 通过。
- [ ] 延伸分支词条不含操作教程，只解释「是什么、什么时候遇到、和 AI 的关系」。

## 7. 增量维护

- 复核周期：工具与价格类 3–6 个月；基础概念 12 个月；发现错误随时置 `needsUpdate`。
- 合并 / 删除词条时同步更新 `related`、搜索索引与旧链接说明。

# 内容审校与溯源规范（M0）

> 本文定义站点内容的「状态、依据、审校与署名」规则。字段实现见 [`src/content.config.ts`](../src/content.config.ts)，展示规则见 [`src/data/content-status.ts`](../src/data/content-status.ts) 与 [`src/components/ContentStatus.astro`](../src/components/ContentStatus.astro)。

## 1. 适用范围

| 内容 | 是否适用 | 说明 |
| --- | --- | --- |
| 学习指南 `guide` | ✅ | 每个模块在页面底部展示内容状态 |
| 术语表 `glossary` | ✅ | 每个词条在页面底部展示内容状态 |
| 作品广场 `works` | ✅ | 策划示例默认按「初稿 + 教学示例」展示 |
| 工具目录 `tools` | 独立规则 | 继续维护 TypeScript 数据，由维护者核对后入库；使用 `verifiedOn` 与工具自身的 `basis`，不套用本文的 frontmatter，也不显示「亲测」「已审核无误」。见 [工具条目规范](CONTENT-GUIDE.md#6-工具数据) |
| 社区 | — | 功能已关闭，页面仅提示暂不开放 |
| 活动 | — | 使用「筹备中 / 暂无排期」状态字段，不套用本文审校状态 |

**总原则**：开发者可以使用 AI 初审、查证和辅助审核，并负责确认最终结论。「已审核无误」表示在记录的审核范围与日期下未发现问题，不表示完全由人工审核，也不保证内容永远正确；没有亲测，就不能写成「亲测」。

## 2. 状态模型

页面状态由 frontmatter 字段**推导**，不需要单独写一个 `status` 字段，避免状态与事实不一致：

| 页面展示状态 | 触发条件 | 页面文案 |
| --- | --- | --- |
| 初稿（默认） | 未填写完整的审核日期与负责人，且 `needsUpdate` 不为 true | 「初稿 · 尚未审核」 |
| 已审核无误 | 同时有 `reviewed` 日期与 `reviewedBy`，且 `needsUpdate` 不为 true | 「已审核无误」+ 审核负责人 / 日期 |
| 待更新 | `needsUpdate: true`（优先级最高） | 「待更新」+ 原因 / 上次审校日期 |

规则：

- **未审核条目默认不得显示成「已审核」**：缺失字段一律按初稿展示。
- **存量内容不需要一次性迁移**：所有字段都有保守默认值。
- **撤销审校**：同时删除 `reviewed` 与 `reviewedBy`，可保留 `reviewNote` 说明原因；也可保留上次审校记录，设置 `needsUpdate: true` 并写明原因，页面会优先显示「待更新」。
- **实质改动重新审校**：修改数据、结论、步骤、工具能力/价格等事实内容后，先同时移除 `reviewed` / `reviewedBy`，或标记 `needsUpdate: true`；复审完成后填写新的审校日期与署名，再清除待更新标记。

## 3. 两个维度：内容依据（basis）与审核结论（reviewed）

「确认审核结论」与「亲自实测」不是一回事，因此分成两组字段：

### 3.1 内容依据 `basis`

| 值 | 含义 | 附加要求 |
| --- | --- | --- |
| `first-hand` | 真实使用经验（本人实际做过、用过） | **必须**填写 `testedOn`（亲测日期）与 `testedEnvironment`（设备 / 平台 / 版本等） |
| `desk-research` | 资料整理（依据官方文档、论文等公开来源） | 建议填写 `sources` |
| `teaching-example`（默认） | 教学示例 / 推演，不是实测 | 不得表述为亲测 |

### 3.2 审核结论 `reviewed` / `reviewedBy`

- `reviewed`：开发者或受委托的审核负责人确认审核结论的日期（`YYYY-MM-DD`）。可以采用 AI 初审与辅助审核，检查范围见第 5 节。
- `reviewedBy`：确认结论的审核负责人，可用笔名或明确填写的匿名代称；必须与 `reviewed` 同时填写，不自动补出负责人。
- `needsUpdate` / `reviewNote`：内容已发现过期或问题、等待更新时使用；`reviewNote` 写原因或审校范围（≤200 字）。

### 3.3 AI 参与 `aiUsage`

| 值 | 含义 |
| --- | --- |
| `none` | 未使用 AI 辅助 |
| `assisted` | AI 用于提纲、润色、翻译、校对等，正文由人撰写 |
| `drafted`（默认） | 较大段落由 AI 起草，作者已核对内容并承担责任 |

默认值是保守的：不写就按「AI 辅助起草」展示。使用 AI 不丢人，冒充原创或伪造亲测才是问题。

`aiUsage` 记录正文的写作方式；只在审核中使用 AI，不必把人工撰写的正文改标为 AI 起草。AI 初审与辅助审核的用途、发现的问题和采用情况记录在 PR / Issue 或仓库文档中，不为此新增页面字段。

### 3.4 贡献者 `contributors`

- 最多 5 个代称，用于展示参与者；**不写真实姓名、学号、手机号、聊天记录**。
- 允许笔名或「某专业同学」这类代称；需要可追溯时，维护组通过 GitHub 账号联系，不公开个人信息。
- 这个字段只负责**单篇内容的署名**；站点级名单（谁参与过、具体做了什么、对应哪个 PR / Issue）记在 [`CONTRIBUTORS.md`](../CONTRIBUTORS.md)，两处不要重复维护。

### 3.5 完整字段示例

以下均为字段写法示例，不代表实际审校记录；请按真实情况填写。标有 `review-fields` 的代码块由 `npm run check:docs` 复用内容检查器验证。

资料整理：不填写亲测日期与环境。

```yaml review-fields
reviewed: "2026-10-21"        # 仅在审核负责人确认结论后填写
reviewedBy: "小林"             # 审核负责人（可笔名）
needsUpdate: false            # 发现过期或问题、等待更新时改 true
reviewNote: "核对了事实与链接，未实测付费额度"  # 可选，≤200 字
basis: "desk-research"
aiUsage: "assisted"           # none | assisted | drafted
contributors: ["小林", "阿哲"] # 可选，≤5 个代称
```

真实使用经验：必须同时提供亲测日期与环境；亲测不等于已经完成内容审核。

```yaml review-fields
basis: "first-hand"
testedOn: "2026-10-21"
testedEnvironment: "网页版，Chrome，个人账号"
aiUsage: "assisted"
```

撤销审校后可保留原因，`reviewed` 与 `reviewedBy` 均不保留：

```yaml review-fields
basis: "desk-research"
aiUsage: "assisted"
reviewNote: "正文步骤已调整，等待重新审核"
```

## 4. 页面展示规则

- 所有指南、术语、作品详情页展示「内容状态」区块（`data-content-status` 便于测试）。
- 展示内容：状态（初稿 / 已审核无误 / 待更新）、内容依据、AI 参与、审核负责人与日期（若有）、贡献者（若有）。
- 状态为「待更新」时提示交叉核对；状态为「初稿」时明确写「尚未审核」。
- 搜索索引保持原有字段，不把内容状态当作排序或可信度信号；搜索到未审校内容时，点开详情页即可看到状态。
- 状态由 frontmatter 推导，不在页面里手工维护，避免「页面写已审核、数据没审校」。

### 指南首页与独立页面正文

指南首页正文 [`src/content/guide/_HOME.md`](../src/content/guide/_HOME.md) 由页面直接导入，不是内容集合条目，不使用普通文章的 frontmatter。首页保持阅读界面，不新增审核信息栏、AI 审核过程或维护清单。

修改知识解释、事实或操作步骤时，在对应 GitHub PR / Issue 中使用第 6 节模板，记录变更范围、来源、AI 初审或辅助审核的用途、结论与负责人；直接提交时，将同样的记录写入仓库文档并关联提交。尚未确认的结论标为「待确认」，不把作者提供正文或 CI 通过当作审核完成。用户可通过 GitHub 仓库文档、PR / Issue 与文件历史查阅这些记录。

其他未使用内容集合的知识性页面沿用此方式；纯排版修改只需记录修改和验证结果，不补写审核结论。

## 5. 审校清单（逐项过）

1. **事实与来源**：每条外部事实有可打开的官方文档 / 原始论文；来源支持正文结论，而不只是同名；没有依据的表述标注「待核实」。
2. **实测证据**：`basis: first-hand` 必须有 `testedOn` / `testedEnvironment`；步骤、截图、失败情况能复现；不能把他人经验写成自己的亲测。
3. **版权与引用**：文字、图片、截图、提示词能说明来源或授权；不整段搬运；引用遵循原站许可。
4. **隐私脱敏**：不出现姓名、学号、联系方式、聊天记录、未公开数据；截图打码。
5. **误导性描述**：不写「最强」「第一」「官方推荐」「必备」；收录不等于推荐。
6. **过期条件**：价格、额度、版本、地区可用性写明核对时间；易变信息不写死。
7. **AI 声明**：`aiUsage` 与实际一致；AI 初稿不得标成人工撰写或亲测。
8. **M0 边界**：示例作品保留「策划示例」标注；活动不虚构日期、场地与人数；不写学校授权或官方合作。

## 6. 角色与责任

- **贡献者**：在 PR / issue 里声明 AI 用途与内容依据；提供可打开的来源；不虚构经历、访谈、数据与评价。可使用笔名，但需保留与维护组联系的 GitHub 账号。
- **开发者 / 审核负责人**：可以安排 AI 初审、来源查证、交叉比对与辅助审核；结合检查结果确认最终结论，再填写 `reviewed`、`reviewedBy`。在 GitHub 记录审核方式与范围，可在 `reviewNote` 写明未覆盖的部分（例如「未实测付费额度」）。
- **维护组**：合并前确认字段与页面展示一致；定期抽查；发现事实问题先把内容置为 `needsUpdate`，再修订和复审。

**红线**：

- Agent 可以执行开发者安排的初审和辅助审核，并整理审核记录；未经审核负责人确认，不自行冒用其署名或补写通过结论。AI 输出与 CI 结果都是审核依据，不自动等于最终结论。
- 不能批量伪造贡献者或审校人。
- 不能为了让页面「好看」而提前填审校日期。

### 审核记录模板（复制到 PR / Issue 或仓库文档）

```text
内容：/guide/… 或 /glossary/… 或 /works/…
版本：对应 PR / 提交链接
范围：事实与来源 / 链接与可复现性 / 隐私与版权 / 误导性描述 / 过期条件
依据：支持本次修改的来源链接或实测记录
审核方式：人工审核 / AI 初审后确认 / AI 辅助审核（写明用途与发现的问题）
结论：待确认 / 已审核无误 / 需修改（列出 1–3 条）
审核负责人：笔名或匿名代称；尚未确认时留空，不代签
日期：YYYY-MM-DD
未覆盖：例如未实测付费额度、未验证地区可用性
```

审核负责人确认结论后，在内容集合条目的 frontmatter 中同时填写 `reviewed`、`reviewedBy`（必要时补 `reviewNote` 说明未覆盖范围），页面会自动从「初稿」切换为「已审核无误」。指南首页等独立页面只保留 GitHub 记录，不追加页面信息。

## 7. 内容生命周期

| 操作 | 要求 |
| --- | --- |
| 新增内容 | 默认显示初稿；PR 中写清依据与 AI 参与；有外部依据时补 `sources` |
| 小改动（错别字、链接、排版） | 可保留原 `reviewed`；若改动涉及事实，按下一条处理 |
| 实质改动（数据、结论、步骤、工具能力/价格） | 同时移除 `reviewed` / `reviewedBy`，或设置 `needsUpdate: true`；重新审校后填写新的日期与署名，再清除待更新标记 |
| 合并 / 拆分条目 | 保留旧 URL 的跳转（M1 需要时）；更新引用与搜索索引；在 PR 说明迁移关系 |
| 撤下内容 | 先置 `needsUpdate` 并在 issue/PR 记录原因，避免无说明的死链；彻底删除需维护组确认 |
| 撤销审校 | 同时移除 `reviewed` / `reviewedBy`，可保留 `reviewNote`；页面回退为初稿，若 `needsUpdate: true` 则显示待更新 |

复核周期建议：工具与价格类内容 3–6 个月；基础概念 12 个月；发现错误随时置为 `needsUpdate`。

## 8. 兼容与迁移

- 未填写审核字段或已完整记录审核日期与负责人的存量 Markdown **不需要迁移**；只填其中一项的记录需补全真实依据，或移除不完整记录。未写其他字段时按 `basis: teaching-example`、`aiUsage: drafted`、`needsUpdate: false` 处理。
- Schema 会拒绝以下不合法组合（构建直接失败，错误信息指出字段）：
  - `reviewedBy` 与 `reviewed` 只填写其中一项；
  - `basis: first-hand` 缺少 `testedOn` 或 `testedEnvironment`；
  - 非 `first-hand` 却填写了亲测字段；
  - 日期不是 `YYYY-MM-DD` 格式；
  - `contributors` 重复或超过 5 个。
- 验证命令：`npm run verify`（类型检查、内容与文档校验、构建、测试、站内链接检查）。

## 9. 后续工作

- 工具目录当前继续使用 TypeScript 数据，不以迁移 Markdown 作为接入前提。未来若统一展示审校状态，需先明确字段含义与迁移方案，避免与工具现有的 `basis: official | docs | community` 混用。
- 内容与页面数量的回归检查已从内容目录推导；后续新增集合或字段时，同步维护 schema、内容检查器与测试。
- M1 开放真实投稿时，再补充「作者授权、真实姓名可选、撤稿流程」等字段，不提前收集个人信息。
